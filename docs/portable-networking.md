# Portable Uno Q networking and capture controls

The Uno Q uses `https://rgb.wehden.com` for every application connection.
Source identity is `unoq`; neither Wi-Fi leases nor Ethernet addresses appear
in service source configuration or network policy. The board needs DNS and
outbound HTTPS. Redis and the 9B Ollama pool remain internal to the cluster.

## Device protocol and authorization

All device requests use `/api/device/unoq`:

- `GET /policy` retrieves settings and current live refinements.
- `POST /live` uploads the latest annotated JPEG and board status. There is
  one pending frame, and network outages do not create a live-frame backlog.
- `POST /observations` delivers immutable observations from the SQLite outbox.
  The board deletes a row only after a JSON acknowledgement with its UUID.

TLS verification is enabled. Origins must use HTTPS and public DNS names.
Redirects are rejected, so an Access login page cannot acknowledge an upload.
The board sends a dedicated Cloudflare Access client ID/secret plus an RGB
bearer scoped to its source. Those values belong in its mode-0600 runtime
file. The service's `DEVICE_TOKENS_JSON` Secret maps source IDs to bearers.
Never put those values, Wi-Fi passwords, or private images in Git.

The protected LaminarAuth route `rgb-device-unoq` grants the service identity
only `/api/device/unoq`. Its ingress retains identity stripping and ForwardAuth.
The device identity cannot browse the dashboard, records, or another source.
Google owner access remains separate. The dedicated `rgb-unoq` Access
credential expires on 2027-10-26; renew it and update the private board file
and registry expiry together. Renewing its Access credential does not require
changing its source ID or historical observations.

Live frames stay in process memory, with a 15-second freshness deadline. They
never enter Redis, image storage, or an observation outbox. HTTP request and
stream buffers are sized to stay in RAM; a real Waitress upload test rejects
any attempt to spool an accepted live request to a temporary file. The relay currently
uses one web replica and one Waitress process, matching `deploy/app.yaml`.
A restart drops the live buffer; new frames refill it. Keep this constraint
when changing replica count or server process count. History uses private
Redis and the existing image archive. The ingest service is ClusterIP-only;
the previous board NodePort and board-IP allowlists are removed at cutover.

## Save networks before a move

Copy `scripts/network-profile.py` onto the Uno Q, then run there:

```sh
sudo python3 network-profile.py wifi --name RGB-Lab --ssid LAB_SSID
sudo python3 network-profile.py ethernet --name RGB-Ethernet
```

The Wi-Fi command prompts privately for a WPA2/WPA3 passphrase. Use
`--security sae` for a WPA3-only profile. The password is never a command-line
argument. Profiles are written atomically with mode 0600 under
`/etc/NetworkManager/system-connections`. Reuse the same name with `--replace`
to update a profile created by this tool. Existing unrelated profiles remain.
802.1X enterprise Wi-Fi needs its identity/certificate configuration through
NetworkManager instead of this personal-network helper.

Both profiles use DHCP and autoconnect. The Ethernet profile matches supported
Ethernet adapters without binding to a USB interface name; its default route
metric is 100, compared with 600 for Wi-Fi profiles generated by this tool.
The helper loads profiles without requesting a connection switch. With the
powered USB-C hub and a supported adapter, plugging in an Ethernet cable can
activate that saved profile. A cable to an isolated network does not provide
Internet access to the public RGB service.

Check `nmcli device status` and `nmcli connection show` before leaving. Keep a
USB/ADB recovery path. Changing networks does not require changing RGB source
URLs, ingest URLs, or IP allowlists. Wi-Fi/Ethernet switching still requires a
physical acceptance test on the intended adapter and lab network.

## Classification, recording, and VLM pause

Local classification has independent Start/Pause controls. Choose **Preview ·
no recording** to run YOLOE and display live boxes without writing frames,
detections, observations, or VLM jobs. Choose **Record observations** to archive
one frame every 15 seconds while classification runs. Pausing classification
leaves the camera on and stops local model inference. Startup waits for the
service policy before classifying or recording. NetworkManager credentials and
control settings are configuration; preview image data stays in memory.

A recorded frame's capture-time settings determine its automatic VLM
eligibility. If VLM was paused then, the frame remains `manual_only` after
resume. The service derives this policy from the audited setting history,
including buffered uploads, and records the policy version. In-flight model
requests finish; pause prevents the next request.

**Catch up now** requests missing VLM readings for the selected source through
a fixed stream watermark. The UI queues pages of at most 100 scanned frames;
frames captured after the click are outside that batch. Each batch records
its operator, boundary, and progress. **Request VLM for this detection** sends
only that numbered crop, with the original scene as context. Requests made
while VLM is paused wait for Resume VLM. Neither action silently resumes it.

Current scenes alternate with historical work. Historical analysis checkpoints
between crop batches when a new scene needs service. Its cursor stays behind
unfinished work, and completed readings are reused on restart. Manual-only
frames are not automatically promoted by a display-mode change.
